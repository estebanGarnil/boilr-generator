# Generated project state contract

This document defines the version 1 contract for tracking projects generated by Boilr.

It defines the architectural invariants implemented by project generation,
status inspection, explicit reconciliation, and safe project updates. It does
not add support for adopting arbitrary existing projects.

For operational CLI usage, see
[Generated project lifecycle](project-lifecycle.md).

## Goals

The generated project state must allow Boilr to:

- identify resources independently from their current paths;
- remember the last successfully applied generation;
- distinguish generated resources from user-created resources;
- detect modifications, deletions, type changes, and possible moves;
- update generated resources without silently overwriting user changes;
- remove only resources that Boilr previously generated;
- preserve untracked files located inside generated directories;
- support module additions and removals through complete project replanning;
- support configurable module destinations;
- prepare resources for future development and production scopes.

## Sources of truth

Boilr uses four distinct sources of information.

### Module manifest

A module manifest defines the module defaults:

- module identity and version;
- source declarations;
- default destinations;
- variables and options;
- capabilities and requirements;
- generated Docker and environment contributions.

Module defaults do not represent user choices.

### Project manifest

`project.yml` describes the desired project.

User choices that must remain reproducible belong in the project manifest. This includes module selection, variables, options, bindings, and future destination overrides.

A destination selected by the user must never exist only in the generated state.

### Generated project state

`.boilr/state.json` describes the last generation that Boilr successfully applied and accepted.

The state is a baseline. It must not silently follow filesystem changes.

### Observed filesystem

The output directory represents the current observed state.

It may contain:

- intact generated resources;
- generated resources modified by the user;
- missing generated resources;
- moved resources;
- user-created untracked resources;
- unsupported or ambiguous filesystem entries.

The observed filesystem never replaces the stored baseline automatically.

## Reserved internal paths

Boilr reserves the following paths inside a managed output:

- `.boilr/state.json`;
- `.boilr/state.pending.json`;
- future files located directly under `.boilr/`.

Internal Boilr paths:

- are not generated project resources;
- are excluded from normal untracked-resource reporting;
- are excluded from ordinary filesystem drift comparison;
- must not be owned by a module;
- must never contribute to their own fingerprints.

`state.pending.json` is a transaction marker and must not be committed.

`state.json` is deterministic project metadata and is intended to be committed with the generated project.

## State invariants

A valid state follows these invariants:

1. Paths are relative POSIX paths.
2. Absolute paths are forbidden.
3. Empty paths, `..`, and paths outside the output root are forbidden.
4. Resource identifiers are unique.
5. Resource identifiers do not depend on destination paths.
6. The output root itself is not a managed resource.
7. `.boilr/state.json` is not listed as a managed resource.
8. Secrets and rendered file contents are never stored in the state.
9. User-created files are never tracked automatically.
10. Directories are never considered exclusive subtrees.
11. A tracked directory may only be removed when empty.
12. A modified tracked resource is never overwritten or removed silently.
13. State transitions are deterministic.
14. Successful execution produces exactly the state prepared by its plan.
15. Dry runs never create or modify state files.
16. Read-only status operations never change the stored baseline.
17. Unsupported state schema versions are rejected explicitly.

## State document

Version 1 has the following conceptual structure:

```json
{
  "schema_version": 1,
  "generator_version": "0.1.0",
  "project": {
    "name": "my_app",
    "type": "fullstack_web",
    "version": "1.0.0",
    "manifest_sha256": "..."
  },
  "modules": [
    {
      "key": "django",
      "version": "1.0.0",
      "origin": "builtin",
      "manifest_sha256": "...",
      "destination": "backend"
    }
  ],
  "bindings": [
    {
      "consumer_module": "django",
      "binding": "primary_database",
      "capability": "database.connection",
      "provider_module": "postgres"
    }
  ],
  "resources": [
    {
      "id": "module:django:render:settings-base",
      "kind": "file",
      "default_path": "backend/config/settings/base.py",
      "desired_path": "backend/config/settings/base.py",
      "materialized_path": "backend/config/settings/base.py",
      "management": "generated",
      "scope": "shared",
      "owner": "django",
      "contributors": [
        "django",
        "django-postgres",
        "django-redis"
      ],
      "content_size": 2048,
      "content_sha256": "...",
      "mode": 420,
      "link_target": null
    }
  ]
}
```

The Python models in `boilr_generator.state` implement these semantics.

## Deterministic serialization

The final state file must be deterministic:

- UTF-8 encoding;
- LF line endings;
- one final newline;
- stable field order;
- resources sorted by identifier;
- modules sorted by key;
- bindings sorted by their stable identity;
- contributors sorted and unique;
- no generation timestamp;
- no absolute machine-specific paths.

Formatting-only changes to `project.yml` must not change `manifest_sha256`.

The project manifest fingerprint must be calculated from a normalized validated representation.

## Project metadata

The project state records:

- project name;
- project type;
- project version;
- normalized manifest fingerprint.

It does not store the complete project manifest because `project.yml` remains the source of user intent.

## Module metadata

Each resolved module records:

- module key;
- declared version;
- origin type;
- normalized module-manifest fingerprint;
- resolved destination.

Version 1 supports the `builtin` origin. Future schema versions may add local and remote origins.

Module variables, options, provider values, and secrets are not copied into the state.

## Binding metadata

Bindings record the resolved relationship between modules.

They include:

- consumer module;
- binding key;
- capability;
- provider module.

Rendered binding values are not stored because they may contain sensitive values.

Recording the resolved provider allows Boilr to detect when the same manifest would resolve differently after registry changes.

## Stable resource identities

A resource identifier describes logical origin, not physical destination.

Moving a resource must not change its identity.

Core-generated resources use reserved identifiers such as:

```text
core:docker-compose
core:environment
```

Rendered module resources use identifiers such as:

```text
module:django:render:settings-base
module:django:render:requirements
```

Copied resources use a stable source declaration identifier and a relative source path:

```text
module:django:copy:apps:core/models.py
module:django:copy:config:settings/local.py
```

Source declarations will require stable identifiers before state persistence is implemented.

Changing a source declaration identifier is a breaking resource migration unless the module explicitly declares a migration.

## Resource kinds

Version 1 recognizes:

- `file`;
- `directory`;
- `symlink`.

Regular generated files record:

- content size;
- SHA-256 fingerprint;
- normalized intended mode when supported.

Directories do not have content fingerprints.

Symbolic links record their link target and are never followed during state capture.

## Default, desired, and materialized paths

Each resource has three path concepts.

### Default path

The path proposed by the module manifest.

### Desired path

The path produced after applying project-level destination choices.

### Materialized path

The path at which the resource existed when the state was successfully recorded.

After a normal successful generation, desired and materialized paths are equal.

After an unconfirmed manual move, the stored materialized path remains unchanged. The possible new location exists only in the observed status until explicitly reconciled.

## Ownership and contributions

Each resource may have:

- one primary owner;
- zero or more contributors.

The owner declares the source that creates the resource.

Contributors influence its final content.

For example, Django may own `backend/requirements.txt`, while `django-postgres` and `django-redis` contribute dependencies to it.

Core aggregate resources such as `docker-compose.yml` may have no module owner and several contributors.

Ownership never means exclusive ownership of a directory subtree.

## Management mode

Version 1 writes only:

```text
generated
```

The field is present to make ownership explicit.

Future state schema versions may support `adopted` and `external`, but arbitrary project adoption is outside the current development phase.

## Resource scopes

Version 1 recognizes these scopes:

- `shared`;
- `development`;
- `production`.

The initial implementation may classify existing resources as `shared`.

The field is included now so future production resources can coexist with development resources without changing stable resource identity semantics.

Implementing production profiles is outside the current development phase.

## Observed project status

The status engine classifies observed resources as:

- `unchanged`;
- `modified`;
- `missing`;
- `moved`;
- `move_candidate`;
- `ambiguous_move`;
- `type_changed`;
- `mode_changed`;
- `untracked`.

A unique untracked file with the same kind and fingerprint as one missing tracked file may become a move candidate.

A move candidate is never accepted silently.

Moved and modified resources cannot be identified reliably from fingerprints alone and require explicit reconciliation.

## User-created resources

A filesystem path absent from the generated state is untracked.

Untracked resources:

- are reported by status;
- are never added to the state automatically;
- are never overwritten automatically;
- are never removed by update, add, remove, or reconcile;
- may exist inside tracked directories;
- prevent deletion of a containing directory while it remains non-empty.

Boilr tracks exact resources, not arbitrary descendants of generated directories.

## Modified generated resources

A resource is modified when its observed representation differs from the stored baseline.

Modification includes:

- different content;
- different resource kind;
- different symbolic-link target;
- relevant permission changes.

A modified generated resource blocks automatic overwrite or removal.

The user must explicitly choose a reconciliation strategy before the operation can continue.

Accepting a modification updates the baseline only through a dedicated reconciliation operation.

## Removal rules

Ordinary lifecycle operations may remove a resource only when:

1. the resource exists in the previous state;
2. the resource is absent from the desired state;
3. the observed resource still matches the previous baseline;
4. the removal path remains inside the output root.

A tracked directory may be removed only after its tracked children have been removed and only when it is empty.

Ordinary lifecycle operations never recursively delete an output subtree.

The existing `replace` strategy must not be used as an ownership rule.

`generate --clean` remains a separate, explicit, destructive operation and may remove untracked resources according to its documented contract.

`add`, `remove`, `update`, and `reconcile` never enable clean behavior implicitly.

## Reconciliation model

Lifecycle planning compares three states:

1. stored baseline;
2. observed filesystem;
3. newly desired project.

Safe automatic operations include:

- creating a desired resource at an unused path;
- replacing an unchanged tracked resource;
- removing an unchanged tracked resource that is no longer desired;
- leaving identical resources unchanged.

Conflicts include:

- overwriting a modified tracked resource;
- deleting a modified tracked resource;
- writing over an untracked resource;
- ambiguous movement;
- unsupported filesystem kinds;
- incompatible destination collisions.

Conflict resolution must be explicit and represented in the final plan.

## Transactional state update

The desired final state is computed during planning.

Execution follows this contract:

1. validate the stored baseline and observed filesystem;
2. create an atomic pending-state marker;
3. apply exactly the accepted filesystem plan;
4. write the final state through a temporary file;
5. atomically replace `state.json`;
6. remove the pending marker.

If execution fails:

- the previous final state remains unchanged;
- the pending marker remains available for diagnostics;
- the next mutating operation refuses to continue automatically;
- a status or recovery command explains the interrupted transition.

Internal state writes must not invalidate the captured output state. `.boilr/` is therefore excluded from ordinary project-state capture and compared separately.

## Existing generated projects

Version 1 does not adopt arbitrary projects.

A future state-initialization command may create state for an existing project only when:

- a valid project manifest is supplied;
- a complete plan can be created;
- every expected generated resource matches the observed output;
- no unexplained managed-resource difference exists.

Initialization writes only the state and does not regenerate project files.

## Deferred capabilities

The following capabilities are intentionally deferred:

- adoption of arbitrary projects;
- semantic analysis of user source code;
- automatic acceptance of moved and modified resources;
- state migrations between arbitrary module layouts;
- Studio;
- remote module registries;
- the module marketplace;
- complete development and production profiles.

The version 1 state contract must not prevent these future additions, but it must not implement them prematurely.
